# Source authority and boundaries

## Authority order

Use the strongest current source rather than blending old and new material:

1. Current approved Project instructions and explicit user revisions.
2. The controlling Scripture passage and exact active reading-plan entry.
3. An approved Study Engine handoff or source-controlled study summary.
4. User pastoral notes and supplied series continuity.
5. Reusable Devotion Builder standards bundled in this plugin.
6. Validated supporting Skills for procedures they own.
7. Legacy GPT instructions, archived agents, old samples, and migration records only as regression evidence.

A newer timestamp alone does not make a source controlling. Approval, role, and Project context matter.

Do not merge conflicting versions silently. Preserve the controlling source and identify a material conflict when it affects the requested output.

A current user request may revise content, scope, or format, but it does not turn memory into an authoritative reading-plan source. For any named, numbered, dated, or scheduled devotional week/day, require the exact active Project entry or another accessible controlling source before building. Do not reconstruct that entry from prior chats, model memory, completed devotional weeks, remembered schedules, or another year's plan, even when the remembered material happens to be correct. If the source is unavailable, request or retrieve it, or clearly offer a separate non-reading-plan passage-based draft.

## Reusable plugin content

The reusable plugin may carry:

- devotional identity and scope;
- five-day devotional movement;
- generic tone and editorial standards;
- reusable command routing;
- source and boundary rules;
- supporting Skill registry;
- generic output formats and review checks.

The reusable plugin must not permanently carry:

- a specific annual reading plan;
- completed devotional weeks as global truth;
- organization-specific permission grants;
- private ministry contacts or credentials;
- project memory or week-continuity records;
- sermon, course, or media project content;
- legacy Agent 002 persona behavior.

Those belong in the active Project or archive.

## Core vs supporting Skills

Keep the core lean. The core writes and edits devotionals. It does not duplicate repeatable procedures already owned by validated Skills.

Use:

- `kv-passage-faithfulness-check` for formal passage-faithfulness evaluation;
- `kv-source-transparency-check` for source classification and disclosure;
- `kv-scripture-formatting-check` for Scripture formatting, attribution, translation labels, permission awareness, and BLB handling;
- `kv-multi-asset-throttle` for scope control across multiple distinct asset families;
- `kv-one-page-handout-generator` for an explicitly requested learner handout from completed teaching;
- `kv-print-ready-packet-polish` for final print cleanup of an existing packet;
- `kv-interaction-evaluator` for interaction recommendation only.

Do not copy those full procedures into the core.

## Upstream study boundary

KV Study Engine owns:

- fresh passage study and exegesis;
- original-language analysis;
- historical and cultural research;
- interpretive comparison;
- canonical or topical biblical-theology tracing;
- research packets and source organization;
- verification of disputed claims that requires study beyond the supplied source.

Devotion Builder may write a straightforward devotional from an assigned passage when no disputed or research-heavy issue blocks responsible drafting. It must not invent research authority merely to avoid an upstream handoff.

## Downstream production boundary

Devotion Builder does not become the default owner of:

- sermons or sermon outlines;
- course modules or lesson architecture;
- slide decks;
- leader guides;
- full workbooks;
- final branded image prompts or generated images;
- audio editing or finished podcast production;
- upload-ready app, blog, email, or social packages;
- scheduling or publication;
- SubSplash platform packaging;
- administrative actions or automation setup.

Preserve source meaning in a concise handoff when downstream work is requested.

## Regression posture

Legacy Devotion Builder behavior is useful for checking parity, especially:

- plan-only requests remain plans;
- approval after an explicit plan-then-build gate executes the pending build rather than merely acknowledging approval;
- locked reading-plan entries remain immutable unless explicitly revised and are never reconstructed from memory;
- the Story -> Worldview -> Heart -> Way -> Worship & Response rhythm remains available;
- daily reflection, prayer, and Finish This Sentence remain part of the standard devotional shape;
- devotional prose remains connected and paragraph-dominant rather than choppy sentence stacks;
- simple social derivatives remain available;
- ministry-domain separation remains enforced.

Legacy behavior does not override the approved modular architecture. Where the old GPT performed work now assigned to Study Engine, supporting Skills, or the media/publishing layer, preserve the user-facing command but route it to the current owner.
